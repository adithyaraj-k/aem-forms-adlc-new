HIGH D7 — DESI artifacts are stale — they describe a different form than the one delivered (primary gate blocker)

Issue
The DESI artifacts consumed for traceability live in the earlier run 2026-07-28-vehicle-registration-form and describe a materially different field inventory: emergencyContactNo, registrationYear, a combined makeModel, rcBookNumber and pucCertificateNumber as fields, State as free text, Gender as a dropdown, Vehicle Type defaulting to "Electric Vehicle", Declaration Date defaulting to today, green/teal headings and buttons, and a different declaration sentence.

The delivered form reproduces that reference at 93.72% pixel match with an exact field-inventory match. "Electric Vehicle" is not even an option in the delivered Vehicle Type list; the reference shows "Select".
Cause
The test cases and user stories were authored against an earlier design iteration and were never re-baselined when the reference screenshot became the authoritative source for this delivery.

Re-run design-form-tests (draftsmith) and re-baseline user-stories.yaml (planwright) against reference.png — the field inventory, control types, colours and defaults it actually shows. Do NOT rewrite the form to satisfy the stale cases: that would regress a 93.72% replica. Also settle the contradiction in the test brief, which asked for "Vehicle Type = Electric Vehicle" and "Date = today" while the reference explicitly shows "Select" and an empty DD/MM/YYYY.

HIGH D8 — Declaration Date accepts a future date

Issue
AC-07.3 / TC-07-004 require Declaration Date to reject future dates. It does not — a future value is accepted silently with no error.
Evidence
Live on DEV author: entering 15/01/2030 in Declaration Date produced no error, while the identical value in Date of Birth was correctly rejected with "Enter a valid date (DD/MM/YYYY) that is not in the future." The model confirms the asymmetry: dateOfBirth has validateDateDDMMYYYY($field.$value) == true() && validateDobNotFuture($field.$value) == true(), whereas declarationDate has only validateDateDDMMYYYY($field.$value) == true().
Cause
The not-in-future guard was applied to dateOfBirth only; declarationDate's validation expression was never extended with it. The validateDobNotFuture function itself works correctly (verified in page scope).
Recommended fix
Extend the declarationDate fd:validate expression to validateDateDDMMYYYY($field.$value) == true() && validateDobNotFuture($field.$value) == true() (the existing function is date-generic, so it can be reused as-is) and add a matching constraintMessages.validationExpression. Leave policyValidTill alone — a future date is legitimate there.

HIGH D6 — Authored validation messages are pre-empted by built-in constraints

Issue
Mobile Number shows "Please match the format requested." and Email Address shows "Specify the value in allowed format : email." instead of the authored copy "Enter a valid 10-digit mobile number." and "Enter a valid email address." TC-02-002 and TC-02-004 fail on message text.
Evidence
Submit-forced validation flagged all three invalid fields (mobileNumber, emailAddress, pinCode) and blocked submission, but only PIN surfaced its authored message ("Enter a valid 6-digit PIN code."). The model shows mobileNumber carries BOTH pattern: "^[0-9]{10}$" and a validationExpression; emailAddress is fieldType: email with a validationExpression. pinCode is a plain number-input with only the expression — which is exactly why it is the one that shows authored copy.
Cause
The built-in pattern constraint and the email field-type format constraint evaluate before the custom validationExpression and claim the message slot. The same ordering makes blur-time validation inconsistent — on blur only PIN produced a message.
Recommended fix
Remove the redundant pattern from mobileNumber and let validateMobile10Digits own the check (or set the constraintMessages.pattern text to the authored copy). For emailAddress, set constraintMessages.format/type to "Enter a valid email address." so whichever constraint wins shows the right words. Re-verify on submit AND on blur.

HIGH D11 — Three measured WCAG 2.1 AA contrast failures

Issue
TC-12-003 requires 4.5:1 minimum. Three token pairs fall short, computed from the theme's own declared hex values.
Evidence
Error/asterisk red #e02020 on page background #e8eef7 = 4.09:1 (needs 4.5 — this is the colour of every inline error message and every required asterisk on the light-blue band). Placeholder #8a97b5 on field fill #ffffff = 2.93:1. Field border #c9d3e6 against #ffffff = 1.51:1 (needs 3.0 under WCAG 1.4.11 non-text contrast). The same red on white (#e02020/#ffffff = 4.78:1) does pass — only the page-background pairing fails.
Cause
The theme's accent red and neutral greys were chosen against white rather than against the #e8eef7 page band the form actually sits on.
Recommended fix
Darken the tokens: error/asterisk red → approximately #c01515 (≈5.3:1 on #e8eef7), placeholder → approximately #5d6a8a, field border → approximately #9aa8c4. Re-run the contrast computation against #e8eef7 (not #ffffff) after the change, since the band is the real backdrop.
