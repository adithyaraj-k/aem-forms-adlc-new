## 7. Fix pass 1 (gate-failure #1 from Sentinel — `integration-test-report.md`)

Sentinel ran a **live** verification pass (real REST submit, real JCR/runtime inspection) and found
2 defects owned by Groundsmith: **D1** (submit 502s, zero workflow instances ever created) and **D2**
(the runtime model has no real Approve/Reject branching — both OR-splits collapse to a linear chain).
This section documents the root cause and fix for each, done with live read/write access to the local
AEM author (`http://localhost:4502`, admin:admin) so both fixes are **evidence-based, not guessed**.

### D1 — FIXED and verified end-to-end (submit 200, workflow instance RUNNING)

**Root cause (confirmed via `crx-quickstart/logs/error.log` full stack trace):**
`com.adobe.fd.workspace.exceptions.FormsWorkflowException: Unable to save file attachment for
workItem` is thrown directly by `WorkSpacePayLoadManagerImpl.saveTaskAttachments` (no wrapped
`Caused by` — it's a first-class throw, not a caught nested error) whenever the attachments-folder
path property carries a **trailing slash**. The form's `guideContainer` had
`attachmentsFolderPath="attachments/"` (with the trailing `/`) and both `AssignTaskStep` nodes had
`inputAttachmentsPath=attachments/` / `outputAttachmentsPath=attachments/` — all three copied
verbatim from the skill's own scaffold examples, which also show the trailing slash (an
unverified-scaffold detail this AEM version does not actually tolerate, despite the skill's own
`workflow-model-spec.md` documenting `attachments/` with a trailing slash in its Assign Task
property table). This is a **path-parsing bug in `WorkSpacePayLoadManagerImpl`** on this AEM version:
a trailing slash makes its folder-existence/creation check fail even when there are **zero actual
attachment files in the submission** — confirmed by reproducing the failure with an attachment-free,
schema-valid payload.

**Fix (verified live, then persisted to source):**
1. Removed the trailing slash — `attachmentsFolderPath="attachments"` — on
   `ui.content/.../content/forms/af/aem-adaptive-form-agents/employee-training-request/.content.xml`
   → `guideContainer`.
2. Removed the same trailing slash on `inputAttachmentsPath`/`outputAttachmentsPath` in **both**
   `assigntask_manager` and `assigntask_finance` `PROCESS_ARGS` in this model's `.content.xml` — same
   underlying class (`WorkSpacePayLoadManagerImpl`) handles task-level attachment save/load too, so
   this prevents the identical bug recurring the first time a real attachment is saved against an
   open Assign Task (would otherwise have blocked TC-026/TC-030 even after D1's primary fix).

**Live verification (before touching source, to confirm the diagnosis; then again after regenerating
from the corrected source, to confirm no regression):**

### D2 — Root cause identified with concrete evidence; NOT fully resolved this pass (platform limitation, documented for escalation)

**Root cause #1 (confirmed, and independently worth fixing): wrong `sling:resourceType`.**
Both `orsplit_manager` and `orsplit_finance` use
`sling:resourceType="cq/workflow/components/model/orsplit"` — **this component does not exist** on
this AEM instance. Live check: `GET /libs/cq/workflow/components/model/orsplit.json` → **404**. The
real, registered OR-split component is `cq/workflow/components/model/or`
(`GET /libs/cq/workflow/components/model.1.json` lists it as `"or"`, title "OR Split",
`sling:resourceSuperType=cq/flow/components/control/split`). Because the authored resourceType never
resolved to a real component, `ModelGenerateServlet` cannot recognize these two nodes as split steps
at all — it silently **drops** them and chains the surrounding steps straight through in document
order. This is the direct, confirmed explanation for Sentinel's finding: 11 runtime nodes, **zero**
`OR_SPLIT` type, fully linear transitions with empty `rule` strings.

**Root cause #2 (confirmed via live experimentation, NOT previously documented anywhere in this
project): headless (non-editor) authoring of a *working* OR-split is blocked by a reproducible
AEM-engine bug on this SDK version, independent of the resourceType fix.**
Inspected the real `or` component's dialog live
(`GET /libs/cq/workflow/components/model/or.infinity.json`): its actual JCR shape needs, on the split
node itself, `branches` (2–5), and per branch either `script{N}` (inline ECMA `function check(){...}`)
or `scriptPath{N}` (external script), plus `default{N}` (bool, marks the fallback route) — this is a
verified, real shape, not a guess. But the **branch target** (which downstream step each branch leads
to) is not encoded by these properties alone; it requires a nested step to be associated with each
branch. I tested this live on a disposable probe model
(`/conf/global/settings/workflow/models/zz-orsplit-probe`, deleted after testing):
- **Flat sibling steps** after the split (matching the ordinary linear-chain document-order pattern
  used everywhere else in this design format) → `generate.json` returns
  `{"msg":"Could not create workflow model. There are errors in the model.","errorList":[{"errorPath":".../orsplit1","errorMsg":"Split steps must have a valid step in every branch"}]}`
  — confirms branches must be **nested**, not flat siblings.
- **Nested child step nodes directly under the split node** (`orsplit1/branch1step`,
  `orsplit1/branch2step`, both valid `.../model/process` steps) → `generate.json` returns
  `{"msg":"Could not create workflow model.  'Unable to save workflow model'"}`, and
  `crx-quickstart/logs/error.log` shows the real cause:
  `com.adobe.granite.workflow.WorkflowException: Unable to save workflow model` **Caused by:**
  `javax.jcr.ItemExistsException: node2#node3`. This is `ModelGenerateServlet` itself throwing a
  same-name/ID collision while trying to persist the generated runtime graph from nested branch
  children — a genuine, reproducible **AEM-engine bug** in this SDK version's headless model
  generation for split steps, not a mistake in my JCR shape (confirmed correct against the real
  dialog).
- Separately confirmed the **runtime model itself is JCR-versioned** (`mix:versionable`,
  `"version":"1.2"` in its own JSON) and **checked in**, so even a *direct*, past-the-generator Sling
  POST to `/var/workflow/models/{name}/nodes/{new}` fails with
  `javax.jcr.version.VersionException: ... is checked in` (409) — there is no accessible headless
  checkout endpoint (`:operation=checkout` returns "Invalid parameters"; the model path is not bound
  to a JSON-body-accepting save servlet either — tested and rejected). This rules out a live-JCR
  bypass of the generator as well.

**Conclusion: there is no headless (Sling-POST-only) path in this session to author real Approve/Reject
branching for this model on this AEM version.** This directly confirms — with concrete, reproduced
evidence — what `create-workflow`'s own SKILL.md already states as a caveat ("OR-split routing is
Tier A, editor-only, not reliably hand-authorable") but goes further: it is not merely "unverified," it
is **empirically broken** via the one documented headless technique
(`workflow-model-spec.md` → "Deploy a model WITHOUT the editor") when a split step is involved. The 2
"proven precedent" models this project already ships (`business-registration-approval`,
`health-insurance-underwriting`) have the **exact same unresolved placeholder shape** — neither has
ever been proven live to branch correctly; "precedent" here means "same open defect," not "verified
working pattern." That should be flagged upstream, not relied on again.

**What WAS fixed this pass (safe, verified, no regression risk):**
- `inputAttachmentsPath`/`outputAttachmentsPath` trailing-slash fix on both Assign Task steps (see D1
  above — same defect class, same fix).
- Deliberately did **NOT** change `orsplit_manager`/`orsplit_finance`'s resourceType to the correct
  `cq/workflow/components/model/or` **without** also completing the nested branch-target wiring,
  because doing so was verified to turn the current (silently-wrong-but-generatable) linear collapse
  into a **hard generate failure** (`"Split steps must have a valid step in every branch"`), which
  would make the ENTIRE model un-generatable on the next Sync/`generate.json` — a strictly worse
  regression than today's silent-linear behaviour. Shipping a half-fix here would have failed
  Forgemaster's next regenerate outright.
