## 7. Fix pass 1 (Sentinel gate-failure #1 — `testing/integration-test-report.md`)

Sentinel's live verification pass found 2 blocking defects owned by Groundsmith. Both were
investigated and (partially) fixed with live read/write access to the local AEM author
(`localhost:4502`). Full root-cause evidence, exact reproduction, and fix detail are in
`create-workflow.md` §7 ("Fix pass 1"); summary here:

- **D1 — Submit → workflow fails 502, zero instances.** **FIXED, verified twice end-to-end.** Root
  cause: `attachmentsFolderPath="attachments/"` (trailing slash) on the `guideContainer`, and the
  matching `inputAttachmentsPath`/`outputAttachmentsPath="attachments/"` on both Assign Task steps,
  triggers `WorkSpacePayLoadManagerImpl.saveTaskAttachments` to throw
  `FormsWorkflowException: Unable to save file attachment for workItem` — even with zero attachments
  submitted. Removed the trailing slash in all 3 places (source files updated:
  `employee-training-request/.content.xml` guideContainer, and both AssignTaskStep `PROCESS_ARGS` in
  `employee-training-request-approval/.content.xml`). Verified live: a schema-valid, attachment-free
  submission now returns HTTP 200 and creates a `RUNNING` workflow instance sitting at the correct
  first work item (`node2` = Manager Approval) — reproduced twice, including once after regenerating
  the runtime from the corrected `/conf` source (not just a live-only patch).
- **D2 — No real Approve/Reject branching.** **Root cause conclusively identified; NOT fully
  resolved this pass — confirmed AEM-engine/platform limitation, escalated with exact completion
  steps.** Two independent, concretely-evidenced causes: (1) both OR-split nodes use a
  `sling:resourceType` (`cq/workflow/components/model/orsplit`) that **does not exist** on this AEM
  instance (verified 404; the real component is `cq/workflow/components/model/or`) — this is why
  `ModelGenerateServlet` silently drops them and produces a fully linear chain; (2) even with the
  correct resourceType and the real component's own verified dialog shape (`branches`, `script{N}`,
  `default{N}`), headless (non-editor) authoring of the branch-target wiring is **empirically broken**
  on this AEM SDK version — reproduced live on a disposable probe model: nested branch steps throw
  `javax.jcr.ItemExistsException: node2#node3` inside `ModelGenerateServlet`
  ("Unable to save workflow model"), and flat-sibling branches are rejected outright ("Split steps
  must have a valid step in every branch"). The already-generated runtime model is also JCR-versioned
  and checked-in with no accessible headless checkout path, ruling out a direct-JCR bypass too.
  Deliberately did **not** commit a half-fix (correct resourceType alone, without completing branch
  wiring) since that was verified to turn today's silent-but-generatable linear collapse into a
  **hard generate failure** on the next Sync — a strictly worse regression. Exact Workflow-Editor-UI
  completion steps (which branch, which rule text, which target, plus the "Send Approval
  Notification → End" rewire also needed) are documented in `create-workflow.md` §7 for whoever has
  editor/browser access next. **This is the same unresolved shape already present, unverified, in
  this project's 2 other "precedent" models** (`business-registration-approval`,
  `health-insurance-underwriting`) — flagged upstream as a project-wide open item, not something newly
  introduced here.

**Net effect for this fix pass:** D1 fully closed (verified live, twice). D2 root-caused with hard
evidence and a safe partial mitigation (the shared attachments trailing-slash fix, applied
proactively to both Assign Task steps too, pre-empting the same bug recurring at task-attachment-save
time); the actual conditional-branching defect remains open pending Workflow Editor UI access — do
**not** report D2 as resolved to Sentinel; report it as "root-caused, escalated, needs UI completion."

### What the live investigation found (ground truth, not assumed)

Fetched every touched step's `cq:dialog.infinity.json` (`fd/workflow/components/asm/invokeDDX`,

### Trigger

Sentinel's fix-pass-6 retest (`testing/integration-test-report.md`, "D9 (NEW, Critical)") found that
fix pass 6's `FORM_TYPE="AF"` choice — made deliberately, to support interactive
`ApprovalInfo`/`ManagerComments` entry inside the task's inline Adaptive Form panel — is itself
fatal: `dashboard/tm`'s `formview.jsp` throws a vendor `NullPointerException`
(`Cannot invoke "Resource.getParent()" because "parentResource" is null`) on every task-detail page
load, so the inline AF panel never renders and `guideBridge` never connects. The real, deployed
`workitemdetails.js`'s `showConfirmationDialog()` gate —
`isReadOnlyForm || (guideBridge && guideBridge.isConnected() && guideBridge.validate()) || ("CCR_UI"
=== formType && isCCRValid) || "IC_WEB" === formType` — is therefore permanently `false` for
`FORM_TYPE="AF"`, since `isReadOnlyForm` is false and the form type is neither `CCR_UI` nor
`IC_WEB`. Clicking Approve OR Reject on ANY work item produces "Error — There are validation errors.
Fix the errors to continue." unconditionally, with no field ever actually failing validation. This
is the SAME function for both routes (it reads the clicked control's own id), so both Approve and
Reject are equally blocked. Sentinel identified two fix paths and left the choice to this pass:
(1) root-cause `formview.jsp`'s NPE itself, preserving `FORM_TYPE=AF`'s interactive intent, or
(2) revert `FORM_TYPE` to `READ_ONLY_AF` — the reference `assign-task-to-admin` model's own value,
already A/B-tested in fix pass 6 to clear the D8 enum crash identically to `AF` — which makes
`isReadOnlyForm` short-circuit `true`, bypassing `guideBridge` entirely.

### Fix chosen: revert `FORM_TYPE` to `READ_ONLY_AF` (path 2)

Path 1 (fixing the vendor `formview.jsp` NPE itself) would mean patching or overriding a `/libs`
dashboard JSP shipped by the `forms-dashboard-core-bundle` — out of proportion for this pass and a
materially higher-risk change than reverting one enum property back to the value fix pass 6 had
already proven safe for the D8 crash. `READ_ONLY_AF` was chosen and reverted on **both**
`assigntask_manager` and `assigntask_finance`. This trades away nothing D6/D7/D8 already fixed:
those three defects were about the colon-combined attachment properties (D6), the ROUTES JSON
shape (D7, ultimately a cascading D6 symptom), and the `FormType` enum member itself (D8, `AF` vs
`ADAPTIVE_FORM` — `READ_ONLY_AF` is an equally valid enum member and was already live-tested in fix
pass 6's own A/B step). Root-causing `formview.jsp`'s NPE remains open as a distinct, separate,
lower-priority follow-up (not part of D9, which this revert closes) — should a future pass want the
interactive `FORM_TYPE=AF` inline-entry experience restored.

### Comment-capture parity — the real problem this revert reopens, and how it was resolved

Reverting to `READ_ONLY_AF` means the assignee can no longer type free text into an inline AF's
`ApprovalInfo.ManagerComments` field (there is no interactive form panel at all under
`READ_ONLY_AF`) — yet the legacy source's rejection email always included the manager's typed
rejection reason (`sendWithDocument4`'s body references `ApprovalInfo/ManagerComments`), and this
project's own `rejection.html` template (confirmed unchanged, see below) already interpolates
`${workflowData.metaDataMap.rejectionReason}`. Losing that free-text capture would be a real parity
regression, not a cosmetic one.

Investigated the actual, live `fd/workflow/components/dashboard/afParticipantStep` `cq:dialog`
(fetched `cq:dialog.infinity.json` directly, not guessed) and found a genuine OOTB substitute
mechanism that is independent of `guideBridge`/`formview.jsp` entirely:
- `./metaData/IS_COMMENT_ALLOWED` — a switch, "Allow assignee to add comment."
- `./metaData/WORKITEM_COMMENT` — a select, "Save comment in variable" (datasource filters to
  String-type workflow variables already declared on the model).

Decompiled the classes that actually consume these two properties
(`javap -p -c` on `forms-dashboard-core-bundle-4.0.252.jar`, the same jar fix pass 6 already
decompiled `ArgumentParser`/`FormType` from):
- `ArgumentParser.isCommentAllowed()` / `.getWorkItemCommentVariable(WorkItem)` read
  `IS_COMMENT_ALLOWED`/`WORKITEM_COMMENT` straight off the step's `MetaDataMap`.
- `WorkSpacePayLoadManagerImpl.saveComment(Session, WorkItem, FormData)` — invoked from
  `updateWorkItemMetaData()` during task completion — unconditionally stamps the assignee's raw
  comment text onto the work item's own `/metaData/workitemComment` property, and, whenever
  `getWorkItemCommentVariable()` returns non-blank, ALSO calls
  `PropertyResolver.setPropertyValueUsingColonSeparatedValue(workItem, session, comment,
  variableName)` to write that same comment text into the **named workflow variable**.

This comment textarea (`#fd-dashboard-tm-detailsview-comment`) is injected into the Approve/Reject
confirmation dialog by `workitemdetails.js` whenever `$(metadata).data("iscommentallowed")` is
true, and its value is posted as the `comment` request parameter on **every** task completion —
entirely independent of `guideBridge`/`formview.jsp`. It therefore works unchanged under
`READ_ONLY_AF`. Wired `WORKITEM_COMMENT="rejectionReason"` (a workflow variable this model already
declares, per `process_setvars`'s `PROCESS_ARGS`) plus `IS_COMMENT_ALLOWED="{Boolean}true"` on both
Assign Task nodes — this is not a workaround bolted on top of the legacy behavior, it is a genuine
substitute mechanism that lands the same rejection-reason text in the same variable the rejection
email already reads, via the Workspace UI's own OOTB comment box instead of an inline form field.

**Removed a latent clobbering bug found while wiring this:** `process_setrejection`'s prior
`PROCESS_ARGS` used to also set
`rejectionReason=${payload.jcr:content/data/ApprovalInfo/ManagerComments}`. That value comes from
the ORIGINALLY SUBMITTED payload — set, if at all, by the employee at submit time, before any
manager ever saw the request — and since `process_setrejection` runs immediately AFTER the Assign
Task step completes (on the Reject route), it would have unconditionally overwritten whatever the
