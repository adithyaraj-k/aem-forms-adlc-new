# Skill: create-submit-action

## Role

You are an expert AEM Forms backend developer for AEM as a Cloud Service.
You generate production-ready custom submit actions for **Adaptive Forms Core
Components**, following Adobe's official guidance. You always handle exceptions,
never leak ResourceResolvers, and always register the action as **both** an OSGi
service **and** a JCR node — both are required.

This skill follows Adobe's documented model. Do not freelance the SPI, the
return-map keys, or the node properties — they are load-bearing and verified
against the Adobe docs linked at the bottom.

---

## Trigger

This skill activates when the developer asks to:
- Create a custom submit action for an Adaptive Form
- Make the Submit button send form data to a REST API / external system
- Trigger an AEM Workflow on form submission
- Send an email with form data on submission
- Store form data to a custom JCR location or database
- Generate a PDF (or file) from the submitted data, upload it to the DAM, and
  download it to the user on submit → use the ONE shared **Custom-Submit-GeneratePDF**
  action (see that section); never scaffold a new action/servlet/clientlib per form

## How form submission flows end-to-end (Adobe model — read first)

This is exactly what happens when a user clicks **Submit** on any Core
Components Adaptive Form, and where your custom action plugs in:

1. The Submit **button** fires `submitForm()` (the `fd:click` / `fd:events`
   rule on the button — already generated by `create-adaptive-form`).
2. The form runtime submits to the **form container** (`guideContainer`). The
   container submits using the **Submit Action** selected on its
   *Configure → Submission* tab in the form editor.
3. The Submission-tab dropdown is populated from every JCR node whose
   `guideComponentType="fd/af/components/guidesubmittype"`. The label shown is
   that node's **`submitService`** value.
4. On submit, `FormSubmitActionManagerService` looks up the OSGi service whose
   `getServiceName()` **equals** the selected node's `submitService` value, and
   calls **`submit(FormSubmitInfo)`** on it — server-side.
5. Your `submit(...)` runs the business logic (REST call, email, workflow, …)
   and returns a `Map<String,Object>`. The runtime reads that map:
   - `GuideConstants.FORM_SUBMISSION_COMPLETE = Boolean.TRUE` → success; the
     runtime then shows the **thank-you page / message configured on the form
     container** (`thankYouOption`, `thankYouMessage`/`redirectUrl`), passing
     any `fd:redirectParameters` you returned.
   - `GuideConstants.FORM_SUBMISSION_ERROR` → an error; the failure is surfaced
     to the form.

> The redirect / thank-you destination is configured **on the form container**,
> not invented inside `submit()`. Your action only signals completion and may
> contribute `fd:redirectParameters`. (See Adobe's tutorials in Sources.)

So the three identifiers MUST line up — this is the single most common failure:

```
getServiceName() (Java)  ==  submitService (JCR node)  ==  label in Submission dropdown
```

## Verified SPI (AEM Forms SDK)

The custom submit action MUST implement this interface:

```java
package com.adobe.aemds.guide.service;
public interface FormSubmitActionService {
    String getServiceName();
    java.util.Map<String, Object> submit(com.adobe.aemds.guide.model.FormSubmitInfo submitInfo);
}
```

- `getServiceName()` returns the **display label** of the action (e.g.
  `"Custom Submit Action"`, `"Core Custom AF Submit"`). This exact string is
  what appears in the Submission-tab dropdown and what the JCR node's
  `submitService` must equal. (Adobe's samples return a human-readable name, not
  a kebab-case id.)
- `submit(...)` declares **no** checked exception — it must never throw; on
  failure it returns an error map.

`FormSubmitInfo` (extends `com.adobe.forms.common.service.FormDataWrapper`)
exposes, among others: `String getData()` (the submitted payload — a String,
JSON or XML), `String getFormContainerPath()`, `Resource getFormContainerResource()`,
`String getLocale()`, `String getFormSubmitter()`, `String getDraftId()`.
There is **no** `getRequest()` and **no** `getThankYouPage()`.

Return-map keys (from `com.adobe.aemds.guide.utils.GuideConstants`):
- `GuideConstants.FORM_SUBMISSION_COMPLETE` → `Boolean.TRUE` on success.
- `GuideConstants.FORM_SUBMISSION_ERROR` → a `GuideValidationResult` on failure.
- `"fd:redirectParameters"` → a `Map` of values forwarded to the thank-you /
  redirect page (optional).

## Java class template

```java
package com.{package}.forms.submit;

import com.adobe.aemds.guide.service.FormSubmitActionService;
import com.adobe.aemds.guide.model.FormSubmitInfo;
import com.adobe.aemds.guide.utils.GuideConstants;
import org.osgi.service.component.annotations.Activate;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.metatype.annotations.AttributeDefinition;
import org.osgi.service.metatype.annotations.Designate;
import org.osgi.service.metatype.annotations.ObjectClassDefinition;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.util.HashMap;
import java.util.Map;

@Component(
    service = FormSubmitActionService.class,
    immediate = true
)
@Designate(ocd = {ActionName}SubmitAction.Config.class)
public class {ActionName}SubmitAction implements FormSubmitActionService {

    private static final Logger LOG = LoggerFactory.getLogger({ActionName}SubmitAction.class);

    // Display label of the action. MUST equal the JCR node's submitService
    // property and the label shown in the form container's Submission dropdown.
    private static final String SERVICE_NAME = "{Action Display Name}";

    @ObjectClassDefinition(name = "{Action Display Name} Submit Action Configuration")
    public @interface Config {
        @AttributeDefinition(name = "API Endpoint URL", description = "Target REST endpoint URL")
        String apiEndpoint() default "https://api.example.com/submit";

        @AttributeDefinition(name = "API Token", description = "Bearer token for API authentication")
        String apiToken() default "";

        @AttributeDefinition(name = "Timeout (ms)", description = "HTTP request timeout in milliseconds")
        int timeoutMs() default 5000;
    }

    private String apiEndpoint;
    private String apiToken;
    private int timeoutMs;

    @Activate
    protected void activate(Config config) {
        this.apiEndpoint = config.apiEndpoint();
        this.apiToken    = config.apiToken();
        this.timeoutMs   = config.timeoutMs();
        LOG.info("{ActionName}SubmitAction activated. Endpoint: {}", apiEndpoint);
    }

    @Override
    public String getServiceName() {
        return SERVICE_NAME;
    }

    @Override
    public Map<String, Object> submit(FormSubmitInfo submitInfo) {

        Map<String, Object> result = new HashMap<>();

        // getData() returns the submitted form data as a String (JSON or XML).
        String formData = submitInfo.getData();
        String formPath = submitInfo.getFormContainerPath();

        try {
            // --- Your custom business logic here (REST/email/workflow/persist) ---
            boolean success = callExternalApi(formData);

            if (success) {
                // Signal success. The runtime then shows the thank-you page /
                // message configured ON THE FORM CONTAINER. Optionally pass
                // parameters forward to that page.
                result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.TRUE);

                // Optional: forward values to the thank-you / redirect page.
                // Map<String, Object> redirectParams = new HashMap<>();
                // redirectParams.put("referenceId", "<generated-id>");
                // result.put("fd:redirectParameters", redirectParams);
            } else {
                result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.FALSE);
                LOG.warn("Submission rejected by downstream system for form: {}", formPath);
            }

        } catch (RuntimeException e) {
            LOG.error("Error in {ActionName}SubmitAction for form: {}", formPath, e);
            result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.FALSE);
        }

        return result;
    }

    private boolean callExternalApi(String formData) {
        // Use java.net.http.HttpClient (Java 11+) or the Sling HttpClient factory.
        // NEVER use the deprecated Apache Commons HttpClient.
        LOG.debug("Submitting form data to: {}", apiEndpoint);
        // implementation here
        return true;
    }
}
```

## JCR submit-action definition node — .content.xml

This node is what makes the action **discoverable** and selectable in the form
editor. Per Adobe's Core Components guidance it is a minimal `sling:Folder`
placed directly under your app folder. The discovery key is
`guideComponentType="fd/af/components/guidesubmittype"` — **not** the path — so
the folder name is free; keep it descriptive.

**Path:** `/apps/{project}/{actionFolder}/.content.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<jcr:root xmlns:jcr="http://www.jcp.org/jcr/1.0"
          xmlns:sling="http://sling.apache.org/jcr/sling/1.0"
    jcr:primaryType="sling:Folder"
    jcr:description="{Action Display Name}"
    guideComponentType="fd/af/components/guidesubmittype"
    guideDataModel="basic,xfa,xsd"
    submitService="{Action Display Name}"/>
```

Rules (verified against Adobe's documented node and the built-in submit types):
- **`submitService`** is load-bearing — it MUST equal the String returned by
  `getServiceName()`. The runtime resolves the OSGi service by this value, and
  it is the label shown in the Submission dropdown.
- **`guideComponentType`** MUST be the literal `fd/af/components/guidesubmittype`
  — this is how AEM finds the node and lists it in the dropdown.
- **`guideDataModel`** is `basic,xfa,xsd` (order is not significant; the set is).
- A basic custom action needs **no** `sling:resourceType` and **no** dialog.
  Only add a dialog/render script if the action requires its own author-time
  configuration fields in the Submission tab.
- Built-in nodes carry **no** `fd:version`, and the `fd` namespace is not
  declared on the root — do not emit `fd:version`.

## Selecting the action on the form (so Submit actually calls it)

Generating the service + node is not enough — an author must point the form's
container at it (or you pre-wire it). After deploy:

1. Open the form in the editor → select the **Adaptive Form Container** → open
   its **Configure** dialog (wrench icon) → **Submission** tab.
2. In **Submit Action**, pick **{Action Display Name}** (your `submitService`).
3. Configure the **Thank You** behaviour (message or redirect page) on the same
   dialog — this is what the user sees after a successful submit.
4. Save. Now clicking **Submit** runs `submitForm()` → your
   `FormSubmitActionService.submit(...)`.

The container persists the selection on the `guideContainer` node. The Submit
button itself needs no change — `create-adaptive-form` already emits the
`fd:click="submitForm()"` rule and `fd:events` pair.

## Workflow trigger pattern

When the requirement is to trigger an AEM Workflow on submit, do it inside
`submit(...)`:

```java
@Reference
private WorkflowService workflowService;

@Reference
private ResourceResolverFactory resolverFactory;

private void triggerWorkflow(String formPath, String formData) {
    Map<String, Object> authInfo = Collections.singletonMap(
        ResourceResolverFactory.SUBSERVICE, "forms-workflow-service");

    // Always use try-with-resources — never call close() manually
    try (ResourceResolver resolver = resolverFactory.getServiceResourceResolver(authInfo)) {
        WorkflowSession wfSession = workflowService.getWorkflowSession(
            resolver.adaptTo(javax.jcr.Session.class));

        WorkflowModel model = wfSession.getModel(workflowModelPath);
        WorkflowData wfData = wfSession.newWorkflowData("JCR_PATH", formPath);
        wfData.getMetaDataMap().put("formData", formData);

        wfSession.startWorkflow(model, wfData);
        LOG.info("Workflow started for form: {}", formPath);

    } catch (WorkflowException | LoginException e) {
        LOG.error("Failed to trigger workflow for: {}", formPath, e);
        throw new RuntimeException("Workflow trigger failed", e);
    }
}
```

System user mapping — add to `ui.config`:
```xml
<!-- org.apache.sling.serviceusermapping.impl.ServiceUserMapperImpl.amended~forms-workflow.xml -->
<jcr:root xmlns:jcr="http://www.jcp.org/jcr/1.0"
          jcr:primaryType="sling:OsgiConfig"
          user.mapping="[{bundle-name}:{subservice}={systemuser}]"/>
```

> Adobe also ships a built-in **Invoke an AEM Workflow** submit action — prefer
> it for plain "start a workflow on submit" needs, and write a custom action
> only when you need extra logic around the workflow start.

## Submit to REST endpoint

### End-to-end flow (map to every implementation decision)

```
Step 1  User fills Adaptive Form
Step 2  Clicks Submit → submitForm() fires (fd:click AST on the Submit button)
Step 3  AEM Forms runtime collects form data
           OOTB path  → browser serialises fields as multipart/form-data (POST)
                         or query parameters (GET, unchecked)
           Custom path → FormSubmitInfo.getData() returns the payload as a
                         String in JSON format (Core Components AF default)
Step 4  HTTP request sent to external REST API
           OOTB path  → Browser makes a DIRECT cross-origin POST to restEndPointUrl
                         ⚠ CORS headers MUST be set on the EXTERNAL server
           Custom path → AEM server makes the call (HttpClient) — no CORS issue
Step 5  External system processes the request
Step 6  API returns response (HTTP status + optional body)
           OOTB path  → AEM cannot inspect the response; any API error is invisible
           Custom path → submit() reads the status code + optionally parses the
                         response body; can forward values via fd:redirectParameters
Step 7  AEM shows success or error message
           success  → GuideConstants.FORM_SUBMISSION_COMPLETE = Boolean.TRUE
                      → runtime shows thankYouMessage / redirectUrl on the guideContainer
           error    → GuideConstants.FORM_SUBMISSION_COMPLETE = Boolean.FALSE  (soft)
                      or FORM_SUBMISSION_ERROR = GuideValidationResult (hard, shows inline)
```

### Decision: OOTB vs. custom

| Situation | Use |
|---|---|
| Simple POST to an external URL, no custom auth/headers, external server has CORS enabled, API errors don't need to surface to the user | **OOTB "Submit to REST endpoint"** — zero code |
| Bearer / OAuth token, custom headers, need to inspect the API response, surface errors to user, server-side secret, no CORS control on external server | **Custom `FormSubmitActionService`** |

### OOTB "Submit to REST endpoint" wiring (no code needed)

The AEM Forms editor exposes the **"Submit to REST endpoint"** action in the form container's
Submission-tab dropdown. When selected, the editor writes on the `guideContainer`:

```
actionType       = "fd/af/components/guidesubmittype/restendpoint"
restEndPointUrl  = "https://your-api.example.com/endpoint"   ← set by author
enableRestEndpointPost = "{Boolean}true"                      ← POST; false = GET
```

The action dialog (screenshot reference) shows:
- **"Mapping for passing field values as Thank You Page request parameters"** (Add button) — optional key→field mappings forwarded to the redirect/thank-you page (Step 7).
- **"Enable POST request"** checkbox — when checked, the browser POSTs form data as `multipart/form-data` to `restEndPointUrl`; when unchecked it GETs with query parameters.

**No Java code, no OSGi service, no JCR submit-action node is required.**

**To wire it in content XML** (when pre-configuring a form via `create-adaptive-form`):
```xml
<guideContainer
    ...
    actionType="fd/af/components/guidesubmittype/restendpoint"
    restEndPointUrl="https://api.example.com/submit"
    enableRestEndpointPost="{Boolean}true"
    thankYouOption="message"
    thankYouMessage="Your form has been submitted successfully." />
```

> ⚠️ **OOTB = browser-side POST → CORS is YOUR problem.**
> The OOTB action makes a **direct browser-to-API request**. The external server MUST respond
> with `Access-Control-Allow-Origin: *` (or the AEM origin) or the browser blocks the response
> with a CORS error — the form appears to submit but the user sees no confirmation and the
> external system receives the data silently. If you cannot control CORS on the external server,
> use the **custom action** (server-side, no CORS).

> ⚠️ **OOTB cannot inspect the API response (Step 6).**
> If the external API returns a 4xx/5xx, AEM shows the thank-you message anyway — there is no
> error path. Use the custom action if API errors must be surfaced to the user.

### Custom REST submit action (auth / response handling / no-CORS)

Use the **Java class template** from the "What to generate" section above. Key points per flow step:

**Step 3 — data format:** `submitInfo.getData()` returns the submitted payload as a **JSON string**
(Core Components AF serialises fields to JSON). Send it directly as `application/json`.

**Step 4 — server-side call (no CORS):** AEM makes the HTTP call, not the browser.

**Step 6 — response parsing:** read the response body; extract a reference ID or error message;
forward useful values to the thank-you page via `fd:redirectParameters`.

**Step 7 — success/error:** map API HTTP status to `FORM_SUBMISSION_COMPLETE` / `FORM_SUBMISSION_ERROR`.

```java
@Override
public Map<String, Object> submit(FormSubmitInfo submitInfo) {
    Map<String, Object> result = new HashMap<>();
    String formData = submitInfo.getData();   // JSON string (Step 3)
    String formPath = submitInfo.getFormContainerPath();

    try {
        HttpClient client = HttpClient.newBuilder()
            .connectTimeout(Duration.ofMillis(timeoutMs))
            .build();

        // Step 4 — server-side HTTP call, no CORS issue
        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create(apiEndpoint))
            .timeout(Duration.ofMillis(timeoutMs))
            .header("Content-Type", "application/json")
            .header("Authorization", "Bearer " + apiToken)
            .POST(HttpRequest.BodyPublishers.ofString(formData))
            .build();

        HttpResponse<String> response = client.send(request,
            HttpResponse.BodyHandlers.ofString());

        int status = response.statusCode();
        LOG.info("REST submit response: HTTP {} for form: {}", status, formPath);

        if (status >= 200 && status < 300) {
            // Step 7 — success: runtime shows thankYouMessage on the guideContainer
            result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.TRUE);

            // Step 6 — optionally parse the response body and forward values to the
            // thank-you / redirect page as request parameters
            // Map<String, Object> redirectParams = new HashMap<>();
            // redirectParams.put("referenceId", parseReferenceId(response.body()));
            // result.put("fd:redirectParameters", redirectParams);

        } else {
            // Step 7 — API error: surface to the user
            LOG.warn("API rejected submission: HTTP {} — {}", status, response.body());
            result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.FALSE);
            // To show an inline error message in the form, return FORM_SUBMISSION_ERROR:
            // result.put(GuideConstants.FORM_SUBMISSION_ERROR,
            //     buildValidationResult("Submission failed: " + response.body()));
        }

    } catch (IOException | InterruptedException e) {
        // Step 7 — network/timeout error
        LOG.error("REST call failed to: {} for form: {}", apiEndpoint, formPath, e);
        Thread.currentThread().interrupt();
        result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.FALSE);
    }

    return result;
}
```

**Step 7 success/error mapping:**

| Return value | What AEM does |
|---|---|
| `FORM_SUBMISSION_COMPLETE = Boolean.TRUE` | Shows `thankYouMessage` / redirects to `redirectUrl` configured on the `guideContainer` |
| `FORM_SUBMISSION_COMPLETE = Boolean.FALSE` | Submission acknowledged as failed; form stays; no specific inline message |
| `FORM_SUBMISSION_ERROR = GuideValidationResult` | Shows the validation result as an inline error on the form |

**OSGi config** (`config` or `config.publish`):
```json
{
  "apiEndpoint": "https://api.example.com/v1/form-submit",
  "apiToken": "$[secret:forms.submit.apiToken]",
  "timeoutMs": 5000
}
```

**Never hardcode secrets** — use `$[secret:{key}]` resolved from AEM Cloud Manager environment variables.

### Common errors

| Symptom | Flow step | Cause | Fix |
|---|---|---|---|
| Submission dropdown shows "Select" (blank) after deploy | Step 2 | `actionType` on `guideContainer` set to generic marker instead of node path | Set `actionType="{project}/fd/af/submitactions/{NodeName}"` (node path relative to `/apps`) |
| OOTB REST action: form submits but external system logs a CORS error | Step 4 | Browser-direct cross-origin POST blocked by missing CORS headers on external server | Add `Access-Control-Allow-Origin` on the external server, OR switch to the custom (server-side) action |
| OOTB REST action: external API gets data but AEM shows thank-you even on 4xx/5xx | Step 7 | OOTB cannot inspect response — no error path | Switch to custom action; map `status >= 400` to `FORM_SUBMISSION_COMPLETE = FALSE` |
| External API expects JSON but receives `multipart/form-data` | Step 3 | OOTB always sends `multipart/form-data` | Switch to custom action with `Content-Type: application/json` |
| HTTP 401 from external API | Step 4 | Missing or wrong token | Store token in Cloud Manager secret; reference via `$[secret:...]` in OSGi config |
| Form submits but external system never receives data (OOTB) | Step 4 | "Enable POST request" unchecked (GET with params) | Check the "Enable POST request" checkbox in the editor dialog |
| Thank-you page receives no reference ID from the API | Step 6 | Response body not parsed / `fd:redirectParameters` not populated | Parse `response.body()` in `submit()` and put values into `fd:redirectParameters` map |

## Agent-orchestrated submit (REST API → Agent → multiple Skills)

### When to use this pattern

When the requirement is: **"On submit, invoke an Agent that fans out to multiple Skills before returning the final response"** — e.g.:

- Form submit → Agent validates data with one Skill → enriches with another → writes to FDM → sends email
- Form submit → Agent calls an external API, processes the result with a Skill, then generates a PDF
- Any multi-step server-side pipeline that is too complex for a single `FormSubmitActionService`

This is the **Agent-orchestrated submit** pattern. The Adaptive Form's custom `FormSubmitActionService` acts as the **entry point**: it POSTs form data to the Agent's REST endpoint, the Agent orchestrates multiple Skills, and the final HTTP response drives the AEM thank-you / error message.

### End-to-end flow

```
Step 1  User fills Adaptive Form
Step 2  Clicks Submit → submitForm() (fd:click AST)
Step 3  AEM Forms runtime → FormSubmitActionService.submit(FormSubmitInfo)
           getData() → form payload as JSON string
Step 4  submit() POSTs JSON to the Agent's REST endpoint (AEM Sling servlet or external)
           Uses java.net.http.HttpClient (server-side → no CORS)
           Bearer token / API key from OSGi config $[secret:...]
Step 5  Agent receives the request and orchestrates Skills:
           Skill A  → validate / transform / enrich the payload
           Skill B  → call external system / FDM / database
           Skill C  → generate PDF / send email / trigger workflow
           (Skills run sequentially or in parallel as the Agent decides)
Step 6  Agent returns a JSON response: { "status": "success"|"error", "message": "...", "referenceId": "..." }
Step 7  submit() reads the response:
           status == "success" → FORM_SUBMISSION_COMPLETE = TRUE
                               → optionally forward referenceId via fd:redirectParameters
           status == "error"   → FORM_SUBMISSION_COMPLETE = FALSE (or FORM_SUBMISSION_ERROR)
                               → log the Agent's error message
Step 8  AEM shows thankYouMessage (success) or surfaces error (failure)
```

### What to generate

The same **4-file scaffold** as any custom REST action (service / JCR node / OSGi config / test), with `submit()` calling the Agent endpoint:

```java
@Override
public Map<String, Object> submit(FormSubmitInfo submitInfo) {
    Map<String, Object> result = new HashMap<>();
    String formData = submitInfo.getData();   // JSON string — Step 3

    try {
        // Step 4 — POST to the Agent's REST endpoint (server-side, no CORS)
        HttpClient client = HttpClient.newBuilder()
            .connectTimeout(Duration.ofMillis(timeoutMs))
            .build();

        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create(agentEndpoint))
            .timeout(Duration.ofMillis(timeoutMs))
            .header("Content-Type", "application/json")
            .header("Authorization", "Bearer " + agentApiToken)
            .POST(HttpRequest.BodyPublishers.ofString(formData))
            .build();

        HttpResponse<String> response = client.send(request,
            HttpResponse.BodyHandlers.ofString());

        // Step 6 — parse Agent's JSON response
        // Expected shape: { "status": "success"|"error", "message": "...", "referenceId": "..." }
        if (response.statusCode() >= 200 && response.statusCode() < 300) {
            String body = response.body();
            String status = extractJsonField(body, "status");
            String referenceId = extractJsonField(body, "referenceId");

            if ("success".equalsIgnoreCase(status)) {
                // Step 7/8 — success: runtime shows thankYouMessage
                result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.TRUE);
                if (referenceId != null && !referenceId.isEmpty()) {
                    Map<String, Object> redirectParams = new HashMap<>();
                    redirectParams.put("referenceId", referenceId);
                    result.put("fd:redirectParameters", redirectParams);   // Step 7 → redirect page
                }
            } else {
                String errorMsg = extractJsonField(body, "message");
                LOG.warn("Agent returned error for form {}: {}", submitInfo.getFormContainerPath(), errorMsg);
                result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.FALSE);
            }
        } else {
            LOG.error("Agent HTTP {} for form: {}", response.statusCode(), submitInfo.getFormContainerPath());
            result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.FALSE);
        }

    } catch (IOException | InterruptedException e) {
        LOG.error("Agent call failed to: {} for form: {}", agentEndpoint, submitInfo.getFormContainerPath(), e);
        Thread.currentThread().interrupt();
        result.put(GuideConstants.FORM_SUBMISSION_COMPLETE, Boolean.FALSE);
    }

    return result;
}

/** Minimal field extractor — replace with Jackson/Gson if available in the bundle. */
private String extractJsonField(String json, String field) {
    // Looks for "field":"value" or "field": "value"
    String pattern = "\"" + field + "\"\\s*:\\s*\"([^\"]+)\"";
    java.util.regex.Matcher m = java.util.regex.Pattern.compile(pattern).matcher(json);
    return m.find() ? m.group(1) : "";
}
```

### Agent response contract (document this with the Agent author)

The `FormSubmitActionService` expects the Agent to return JSON with this shape:

```json
{
  "status": "success",          // required: "success" | "error"
  "message": "...",             // optional: human-readable description (logged on error)
  "referenceId": "abc-123"      // optional: forwarded to thank-you page via fd:redirectParameters
}
```

Any deviation (different field names, non-JSON response) must be handled in `extractJsonField()` or by switching to a proper JSON parser. **Agree on this contract before implementation** — it is the interface between the form layer and the Agent layer.

### Common errors

| Symptom | Cause | Fix |
|---|---|---|
| Agent receives request but submit always fails | Agent response not matching expected JSON shape | Check `extractJsonField()` against actual response; add debug logging of `response.body()` |
| Submit times out (user sees error) | Agent's multi-skill pipeline exceeds `timeoutMs` | Increase `timeoutMs` in OSGi config; optimise Agent's skill fan-out |
| `referenceId` missing from thank-you page | Agent returns it but `fd:redirectParameters` not wired on the redirect page | Add `{referenceId}` as a query param on `redirectUrl`, or use `thankYouOption="message"` + embed in `thankYouMessage` |
| 401 from Agent endpoint | Wrong or missing `agentApiToken` | Check Cloud Manager secret `forms.agent.apiToken`; verify token format expected by Agent |

## Shared, generic "Custom-Submit-GeneratePDF" submit action (create ONCE, reuse for EVERY form)

For the "on submit, make a PDF of the form, upload it to the DAM, and download it to
the user" requirement, the project has **exactly one** shared submit action —
`Custom-Submit-GeneratePDF` — plus **one** servlet and **one** clientlib. They are
generic (form-agnostic) and created a single time for the whole project. **Never
scaffold a new submit action, servlet, or clientlib per form.** To give any new form
this behaviour the author simply selects **Custom-Submit-GeneratePDF** in the form
container's Submission dropdown — no new code.

> ⚠️ **Idempotency rule — check before you generate.** When asked for "generate a PDF
> on submit / upload to DAM / download" for a form, FIRST check whether the shared
> artifacts already exist:
> - submit-action node `/apps/{project}/fd/af/submitactions/Custom-Submit-GeneratePDF` (under the
>   editor-scanned submitactions path; if a legacy one exists at the project root, MOVE it here)
> - service `CustomSubmitGeneratePDFAction` (`getServiceName()` == `Custom-Submit-GeneratePDF`)
> - servlet `GeneratePDFServlet` (path `/bin/{project}/generate-pdf`)
> - shared clientlib `/apps/{project}/clientlibs/clientlib-generate-pdf` (category `{project}.forms.generate-pdf`)
>
> If they exist, generate **NOTHING** — just tell the author to pick **Custom-Submit-GeneratePDF**
> in the Submission dropdown (and, if not loaded globally, set the form's
> `clientLibRef="{project}.forms.generate-pdf"`). Create the four shared artifacts only
> when they are absent. Do **not** rename them per form, do **not** duplicate the servlet
> or clientlib per form.
>
> ⚠️ **The submit-action node MUST live under `/apps/{project}/fd/af/submitactions/` — NOT at the
> project root `/apps/{project}/Custom-Submit-GeneratePDF`.** The AEM Forms editor's Submission-tab
> "Submit action" dropdown only lists config nodes it discovers under the `fd/af/submitactions`
> search path. If the node sits at the project root, the action STILL fires at runtime (the
> `submitService` value binds server-side), but the editor dropdown shows **"Select"** (blank) and
> the author cannot see/select it — a real, reported bug. Put it at
> `/apps/{project}/fd/af/submitactions/Custom-Submit-GeneratePDF` alongside every other custom
> submit action. If a pre-existing shared node is at the root, MOVE it there (and delete the old
> root node via the filter).

> ⚠️ **Submit AND PDF generation must be GATED on validation success.** Submission and the
> PDF / Document-of-Record generation fire ONLY when ALL form validation passes. An invalid form must
> BLOCK submission, show inline error messages, scroll/focus to the first invalid field, and produce
> **NO PDF**. Keep `Custom-Submit-GeneratePDF` as the **native validating submit** (the Core
> Components submit runs validation before calling the action) — never a raw button `onClick` that
> POSTs to the `GeneratePDFServlet` unconditionally. If the PDF is produced by the clientlib, gate the
> POST on form validity (check the guideBridge/model validity) or, preferably, drive it from the
> native submit so validation always precedes generation. A traceable test must assert: an empty /
> invalid form shows errors and produces NO PDF; a valid form submits AND generates the PDF.

### End-to-end flow (identical for every form)

1. Author selects **Custom-Submit-GeneratePDF** as the form's submit action (dropdown).
2. The single shared clientlib is loaded on the form; on **Submit** (capture-phase, ONLY after the
   native submit's validation passes — never on an invalid form) it collects EVERY field generically
   as `aria-label: value` (no form-specific field names) and POSTs them to the single servlet.
3. `GeneratePDFServlet` (one, shared): generates the PDF, **uploads it to the DAM** under
   `/content/dam/{project}/` (service-user resolver), and **streams it back** with
   `Content-Disposition: attachment` → the browser auto-downloads it.
4. The server-side `Custom-Submit-GeneratePDF` action acknowledges the submission
   (returns `FORM_SUBMISSION_COMPLETE`) so the form shows its thank-you message.

Because data is collected generically (label/value of whatever fields the form has) and
the servlet just renders those lines, the SAME action + servlet + clientlib work for
EVERY form — flight booking, enrollment, contact-us, anything.

**2) Submit-action service** — `CustomSubmitGeneratePDFAction implements FormSubmitActionService`
`getServiceName()` returns `"Custom-Submit-GeneratePDF"`; `submit()` returns
`GuideConstants.FORM_SUBMISSION_COMPLETE = Boolean.TRUE`. (PDF/DAM/download is performed
by the clientlib→servlet; this acknowledges the submission so the thank-you page shows.)

**3) The generic servlet** — `GeneratePDFServlet` (ONE, path-bound, shared):

```java
@Component(service = Servlet.class, property = {
    "sling.servlet.methods=POST",
    "sling.servlet.paths=/bin/{project}/generate-pdf"   // ONE fixed endpoint for ALL forms
})
public class GeneratePDFServlet extends SlingAllMethodsServlet {
    @Reference private transient ResourceResolverFactory resolverFactory;
    @Override protected void doPost(SlingHttpServletRequest req, SlingHttpServletResponse resp) throws IOException {
        String title    = req.getParameter("title");     // generic — supplied by the clientlib
        String content  = req.getParameter("content");   // generic "Label: Value" lines, any form
        String fileName = req.getParameter("filename");
        byte[] pdf = buildPdf(title, content);            // zero-dependency PDF 1.4 + Helvetica
        storeInDam(pdf, fileName);                        // upload to /content/dam/{project} (service user)
        resp.setContentType("application/pdf");
        resp.setHeader("Content-Disposition", "attachment; filename=\"" + fileName + "\"");
        resp.getOutputStream().write(pdf);                // stream back → browser auto-downloads
    }
}
```

- DAM upload uses a **service-user** resolver + `AssetManager.createAsset(...)` (never the
  request/admin resolver), in try-with-resources, with a timestamped unique name.
- Generate the PDF with **no new Maven dependency** (hand-written PDF 1.4 + built-in
  Helvetica) so offline/locked-down builds work.
- It reads only generic params (`title`, `content`, `filename`) — so it is form-agnostic
  and never needs a per-form variant.
- **Empty-content guard — do NOT use `if (lines.isEmpty())`.** `"".split("\\r?\\n")` returns `[""]`
  (a one-element array with the empty string), NOT `[]`, so a `lines.isEmpty()` check never fires and
  an empty submission produces a **silently blank PDF** page. Guard on "no NON-BLANK line" instead:
  ```java
  boolean hasData = false;
  for (String line : lines) { if (line != null && !line.trim().isEmpty()) { hasData = true; break; } }
  if (!hasData) { lines.clear(); lines.add("No form data was submitted."); }
  ```
  Cover it with a unit test that asserts the placeholder text is present **in the PDF byte stream** for
  an empty submission (DESI "empty/null path handled"), and verify live: POST with no `content` → the
  served PDF contains the placeholder line.

**4) The generic clientlib** — `/apps/{project}/clientlibs/clientlib-generate-pdf`
(`cq:ClientLibraryFolder`, `allowProxy="{Boolean}true"`,
`categories="[{project}.forms.generate-pdf]"`, `dependencies="[core.forms.components.runtime.all]"`).
One generic script collects any form's data and downloads the response:

```js
(function () {
  "use strict";
  var URL_ = "/bin/{project}/generate-pdf";
  var CSRF_URL = "/libs/granite/csrf/token.json";
  // The shared PDF clientlib MUST attach the CSRF token ITSELF — do NOT rely on
  // the host page loading Granite's csrfFetchSupport. The standalone AF page loads
  // it (auto-injecting the "CSRF-Token" header on same-origin POSTs), but a custom
  // Sites page that inline-embeds the form does NOT, so a tokenless POST is rejected
  // 403 by Granite's CSRFFilter. Fetch the token and set the header here; degrade
  // gracefully to null (never throw) so standalone pages keep working.
  function csrfToken() {
    try {
      return fetch(CSRF_URL, { credentials:"same-origin" })
        .then(function (r){ return r.ok ? r.json() : null; })
        .then(function (d){ return (d && d.token) ? d.token : null; })
        .catch(function (){ return null; });
    } catch (e) { return Promise.resolve(null); }
  }
  document.addEventListener("click", function (e) {
    var n = (e.target && e.target.nodeType === 1) ? e.target : (e.target && e.target.parentElement);
    var btn = n && n.closest ? n.closest(".cmp-adaptiveform-button__widget") : null;
    if (!btn) return;
    var form = btn.closest(".cmp-adaptiveform-container"); if (!form) return;
    var lines = [];
    form.querySelectorAll("input, select, textarea").forEach(function (el) {
      var t = (el.type || "").toLowerCase();
      if (["submit","button","reset","hidden","file"].indexOf(t) > -1) return;
      if (t === "radio" && !el.checked) return;
      var label = el.getAttribute("aria-label") || el.name || "Field";
      var val = (el.tagName === "SELECT") ? (el.options[el.selectedIndex]||{}).text
              : (t === "checkbox") ? (el.checked ? "Yes" : "") : el.value;
      if (val && String(val).trim()) lines.push(label + ": " + val);
    });
    if (!lines.length) return;
    var title = ((form.querySelector(".cmp-adaptiveform-container__title")||{}).textContent || "Form Submission").trim();
    var body = new URLSearchParams();
    body.append("title", title);
    body.append("filename", title.replace(/\s+/g,"-") + ".pdf");
    body.append("content", lines.join("\n"));
    // Attach the CSRF token before POSTing so it works on ANY host page (standalone OR embedded).
    csrfToken().then(function (token) {
      var headers = { "Content-Type":"application/x-www-form-urlencoded; charset=UTF-8" };
      if (token) headers["CSRF-Token"] = token;
      return fetch(URL_, { method:"POST", credentials:"same-origin", headers: headers, body: body.toString() });
    })
      .then(function (r){ if (!r.ok) throw new Error("status "+r.status); return r.blob(); })
      .then(function (blob){ var u=URL.createObjectURL(blob), a=document.createElement("a");
        a.href=u; a.download=body.get("filename"); document.body.appendChild(a); a.click(); a.remove();
        setTimeout(function(){URL.revokeObjectURL(u);},1000); })
      .catch(function (err){ if (window.console) console.error(err); });
  }, true);   // capture phase — runs before the runtime swaps in the thank-you DOM
})();
```

> ⚠️ **The shared PDF clientlib MUST attach the CSRF token itself — never rely on the host page
> loading csrfFetchSupport.** Granite's `CSRFFilter` rejects tokenless same-origin POSTs with **403**.
> The AEM Forms **standalone** AF page loads Granite's `csrfFetchSupport` clientlib (which monkey-patches
> `window.fetch` to auto-inject the `CSRF-Token` header), so a tokenless `fetch()` silently succeeds
> there. But a **custom Sites page** that inline-embeds the form (e.g. the "Test Adaptive Form" page)
> does **not** load csrfFetchSupport, so the identical tokenless POST is rejected **403** before it
> reaches the servlet. Because this is the ONE shared, form-agnostic clientlib meant to run on ANY host
> page, it must GET `/libs/granite/csrf/token.json` and set the `CSRF-Token` request header on the POST
> itself (degrading to null → no header if the GET fails, never throwing). Do NOT drop this and assume
> the host page supplies the token.

### Loading the one shared clientlib on a form (no per-form copy)

The clientlib only needs to run on forms that use this action. Two options, both reuse
the single library:

- **Per-form opt-in (simplest):** set the form's `clientLibRef="{project}.forms.generate-pdf"`
  on its `guideContainer`. (Trivial, and the author is already selecting the submit action.)
- **Load on every form, zero per-form edit:** `embed` `{project}.forms.generate-pdf` into the

Either way there is still only ONE clientlib — never a per-form copy. The script
self-gates (it only POSTs when a submit button inside a form container is clicked), so it
is safe to load broadly.

> **Headless / JS-disabled:** if the PDF must be produced server-side even without the
> clientlib, move the generate + DAM-upload into `Custom-Submit-GeneratePDF`'s `submit()`
> and return the asset path in `fd:redirectParameters`; the servlet then only streams the
> download. Still one action, one service — never per form.
