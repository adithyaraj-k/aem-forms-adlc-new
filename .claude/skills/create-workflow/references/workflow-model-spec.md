# Workflow Model Node Specification (AEM as a Cloud Service)

Reference: https://experienceleague.adobe.com/en/docs/experience-manager-cloud-service/content/create-form-centric-workflows/aem-forms-workflow-step-reference

Project tokens: `{project}` = `aem-demo-site` (the single project namespace; the folder segment under `/content/forms/af`, `/content/dam/formsanddocuments`, and `/conf/forms` is also `{project}` — there is no separate app folder).

> ⚠️ **Accuracy caveat — read first.** Adobe documents AEM Forms workflow steps as **editor UI**
> configuration, not raw `cq:WorkflowModel` XML. The official step reference gives **no `PROCESS`
> class name and no `PROCESS_ARGS` string** for the Assign Task / Sign / Generate DoR steps. The
> XML node templates below are a **scaffold / visual reference** to recreate the same shape in the
> Workflow editor and to review diffs — the `PROCESS=`/`PROCESS_ARGS=` values are **unverified** and
> may differ by Core Components / Forms version. The **authoritative configuration is the documented
> UI field list** (see "Assign Task — documented UI fields" below). Build the model in the editor,
> **Sync**, then capture `/conf/global/settings/workflow/models` + `/var/workflow/models` to source
> control. Do not present the scaffold XML as final, copy-paste-and-run output.

---

## Where models live on AEMaaCS (deploy `/conf`; `/var` is generated)

| Representation | Path | Format | Deploy? |
|---|---|---|---|
| Design model (source of truth) | `/conf/global/settings/workflow/models/{workflowName}` | editor page: `cq:Page` + `cq:PageContent` with a `flow` parsys of step components (`nt:unstructured` + `sling:resourceType`) — **not** `cq:WorkflowModel` | **YES — commit & package this** |
| Runtime model (executable) | `/var/workflow/models/{workflowName}` | `cq:WorkflowModel` / `cq:WorkflowNode` / `cq:WorkflowTransition` | **Generated by Sync** — don't hand-author; package only to ship the runtime without a manual Sync |

- The **`/conf` design model** is the deployable source of truth. Build/refine it in the Workflow
  editor, then capture the `cq:Page` tree into `ui.content`. **Never write a `cq:WorkflowModel`
  into `/conf`.**
- The **`/var` runtime** is what the submit action and `startWorkflow` resolve — but it is
  **generated from the design model by Sync**, not hand-authored. After deploying `/conf`, open the
  model in the editor once and **Sync** (or package the generated `/var` tree). Deploying only
  `/var` makes the model appear **"not editable"**; deploying only `/conf` without a Sync means the
  runtime may not exist yet.
- The `cq:WorkflowModel` XML in this file and the template references is a **logical/flow
  reference** — use it to plan the model and configure steps in the editor and to review diffs.
  It is **not** the deploy artifact and the `PROCESS`/`PROCESS_ARGS` values in it are unverified.
- **Never** use `/etc/workflow/models` (legacy 6.5) or write to `/libs`.

> You must be in the `workflow-editor` group to create/edit models in the UI.

### ⚠️ Hand-authored `/var` `cq:WorkflowModel` FAILS the build — do not commit it

Writing `ui.content/.../jcr_root/var/workflow/models/{name}/.content.xml` as a `cq:WorkflowModel`
**fails** the `ui.content` filevault `validate-package` (jackrabbit-nodetypes) step with errors like:
`Property 'jcr:title' [String] is not allowed in node with types [cq:WorkflowModel]`,
`Property 'version' ...`, `Property 'x'/'y' ... not allowed in [cq:WorkflowTransition]`, and
`Node '{name} [cq:WorkflowModel]' is not allowed as child of [nt:folder]`. The runtime model is
**generated output**, not source. Never put it in `ui.content`. (This is why the existing
`form-submission-notification` model was authored in the editor and never committed.)

### Deploy a model WITHOUT the editor (verified on this SDK)

When you can reach the running instance, create the `/conf` design model and generate `/var`
programmatically — no manual clicking. Copy the exact shape from any existing model
(`GET /conf/global/settings/workflow/models/{existing}/_jcr_content.10.json`):

1. **Create the `/conf` design `cq:Page`** via Sling POST:
   - `{model}` node = `cq:Page`
   - `{model}/jcr:content` = `cq:PageContent`, `cq:template=/libs/cq/workflow/templates/model`,
     `sling:resourceType=cq/workflow/components/pages/model`,
     `cq:designPath=/libs/settings/wcm/designs/default`, `jcr:title={Title}`
   - `{model}/jcr:content/flow` = `nt:unstructured`, `sling:resourceType=foundation/components/parsys`
   - one step per child, e.g. `flow/process_x` =
     `sling:resourceType=cq/workflow/components/model/process` +
     `metaData/PROCESS={fqcn}` + `metaData/PROCESS_AUTO_ADVANCE=true`.
     START/END are added automatically when the runtime is generated — don't author them in `/conf`.
2. **Generate the `/var` runtime:** `POST {model}/jcr:content.generate.json` →
   `com.adobe.granite.workflow.console.servlet.ModelGenerateServlet`. Success returns
   `{"msg":"Model successfully generated.","modelPath":"/var/workflow/models/{name}"}`. Creating
   `/conf` alone does **not** auto-generate `/var`; the submit action can't resolve the model until
   this runs. (Sibling POST selectors on the same servlet: `override.json`, `revert.json`, `copy.json`.)

**Every POST needs a CSRF token + Referer** (the `CSRFFilter` rejects non-browser POSTs otherwise —
this applies to the Sling node creation in step 1, the `generate.json` in step 2, and the
`/var/workflow/instances` test below). Fetch a token once and send it on each call:
```bash
CSRF=$(curl -s -u admin:admin http://localhost:4502/libs/granite/csrf/token.json | sed -E 's/.*"token":"([^"]+)".*/\1/')
curl -s -u admin:admin -X POST -H "CSRF-Token: $CSRF" -H "Referer: http://localhost:4502/" \
  "http://localhost:4502/conf/global/settings/workflow/models/{name}/jcr:content.generate.json"
```

Gotchas when scripting this on Windows / Git-Bash:
- **MSYS mangles leading-slash values** (`/libs/...` → `C:/Program Files/Git/libs/...`) in curl
  `-F` fields and URLs. Always `export MSYS_NO_PATHCONV=1`. Relative `sling:resourceType` values and
  FQCNs (dots, no slash) are unaffected.
- **`/tmp` and `@file` uploads can fail (curl exit `000`)** under Git-Bash because `/tmp` isn't
  writable there. Write the payload file to a real Windows path and run `curl.exe` from PowerShell
  (native path handling), e.g. `-F "data.xml=@$env:TEMP\data.xml;type=application/json"`.
- A `cq:WorkflowModel` GET with a numeric or `infinity` selector returns "Unknown version selector"
  (the node is versionable). Use a plain `.json` / `.tidy.json` to inspect it.
- **Test a model fast** (no form submit / publish needed): create a payload folder with a child
  `data.xml` (JSON is fine — `{...}`), then `POST /var/workflow/instances` (with the CSRF+Referer
  headers) `-F model=/var/workflow/models/{name} -F payloadType=JCR_PATH -F payload={folder}
  -F _charset_=utf-8`. A `201` with a `Location` of `/var/workflow/instances/...` means it started;
  the auto-advancing process step then runs and writes its output. If the start returns
  `400 "workflow model not found"`, verify **both** before blaming the model path: (a) the runtime
  exists and is registered — `generate.json` returned success **and** the model lists at
  `/libs/cq/workflow/admin/console/content/models.html` (registration can lag a moment after
  generate); and (b) the payload folder actually has a child `data.xml`. In one observed run the
  start failed until the `data.xml` was present; the error text points at the model but the payload
  was the missing piece.

## Workflow Stages

Stages show progress in the AEM Inbox. Define them in the model's `metaData/stages` before
referencing them from steps. Example for a mortgage application:
`Loan Request → Under Review → To Be Signed → Completed`. Each Assign Task step names the stage
it belongs to via `workflowStage`.

---

## Runtime Model Root Node (cq:WorkflowModel XML)

`ui.content/src/main/content/jcr_root/var/workflow/models/{workflowName}/.content.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<jcr:root xmlns:jcr="http://www.jcp.org/jcr/1.0"
          xmlns:cq="http://www.day.com/jcr/cq/1.0"
          xmlns:nt="http://www.jcp.org/jcr/nt/1.0"
          jcr:primaryType="cq:WorkflowModel"
          jcr:title="[WORKFLOW_TITLE]"
          description="[DESCRIPTION]"
          version="1">
  <metaData jcr:primaryType="nt:unstructured" tags="[]">
    <stages jcr:primaryType="nt:unstructured">
      <stage0 jcr:primaryType="nt:unstructured" title="Application Submitted"/>
      <stage1 jcr:primaryType="nt:unstructured" title="Under Manager Review"/>
      <stage2 jcr:primaryType="nt:unstructured" title="HR Review"/>
      <stage3 jcr:primaryType="nt:unstructured" title="Completed"/>
    </stages>
    <variables jcr:primaryType="nt:unstructured">
      <!-- see Variables section -->
    </variables>
  </metaData>
  <nodes jcr:primaryType="nt:unstructured">
    <!-- step nodes -->
  </nodes>
  <transitions jcr:primaryType="nt:unstructured">
    <!-- transition nodes -->
  </transitions>
</jcr:root>
```

### Assign Task — documented UI fields (AUTHORITATIVE — configure these in the editor)

This is what Adobe actually documents. Drag **Assign Task** onto the model and set these in its
properties dialog (tabs vary slightly by version):

- **Basics:** Title, Description, Priority (`High`/`Medium`/`Low`), **Workflow Stage**, Thumbnail.
- **Form/Document:** Type (`Adaptive Form`, read-only Adaptive Form, non-interactive PDF); method
  to locate the form; **Adaptive Form Path** (`/content/forms/af/{project}/{formName}`).
- **Assignee:** Assign to a specific user/group, or **dynamically** via a Participant Chooser
  script; user/group selection.
- **Notifications:** Send Notification Email, Recipient Email Address, HTML Email Template.
- **Data (input/output):** Pre-populated data file; input attachments; **Save output data file**;
  Save attachments; **Save Document of Record** (path relative to payload, or a variable).
- **Routes & Route Variable:** **Route Variable** name (use `actionTaken`); Routes with titles and
  Coral icons (e.g. `Approve`, `Reject`).
- **Due date:** Days/Hours Until Completion; Time-out after Due Date; Timeout Handler.
- **Additional:** Allow Delegation; Share Settings; allow comments/attachments; show data from
  previous/subsequent steps.

### Assign Task Step — scaffold XML (UNVERIFIED — recreate in editor, do not ship as-is)

```xml
<node1 jcr:primaryType="cq:WorkflowNode" title="Manager Review" type="PROCESS" x="160" y="280">
  <metaData jcr:primaryType="nt:unstructured"
    PROCESS="com.adobe.fd.workflow.aem.process.AssignTaskStep"
    PROCESS_AUTO_ADVANCE="false"
    PROCESS_ARGS="taskTitle=Manager Review — [FORM_TITLE]
      taskDescription=Please review and take action on the submitted form.
      taskPriority=MEDIUM
      taskDueDateInterval=2
      taskDueDateIntervalUnit=DAYS
      notifyParticipant=true
      assignee=[USER_OR_GROUP]
      assigneeType=STATIC
      workflowStage=Under Manager Review
      formType=ADAPTIVE_FORM
      formPath=/content/forms/af/{project}/[FORM_NAME]
      formReadOnly=false
      routeVariable=actionTaken
      routes=Approve,Reject
      inputDataFile=[Payload_Directory]/workflow/data.xml
      inputAttachmentsPath=[Payload_Directory]/attachments/
      outputDataFile=[Payload_Directory]/workflow/data.xml
      outputAttachmentsPath=[Payload_Directory]/attachments/
      outputDoRPath=[Payload_Directory]/DocumentofRecord/DoR.pdf"/>
</node1>
```

**Assign Task property reference:**

| Property | Description | Values |
|---|---|---|
| `taskTitle` | Shown in AEM Inbox | String |
| `taskDescription` | Task details | String |
| `taskPriority` | Inbox priority | `HIGH`, `MEDIUM`, `LOW` |
| `taskDueDateInterval` / `taskDueDateIntervalUnit` | Overdue threshold | Integer / `DAYS`,`HOURS` |
| `notifyParticipant` | Send email | `true`/`false` |
| `assignee` / `assigneeType` | Who / how resolved | String / `STATIC`,`DYNAMIC`,`VARIABLE` |
| `participantChooser` | ECMA script (dynamic) | `/apps/{project}/workflow/scripts/…` |
| `workflowStage` | Stage label | must match a defined stage |
| `formType` | Task form rendering | `ADAPTIVE_FORM`,`READ_ONLY_ADAPTIVE_FORM`,`NON_INTERACTIVE_PDF` |
| `formPath` / `formReadOnly` | Form to render / editability | CRX path / `true`,`false` |
| `routeVariable` | Captures clicked action | e.g. `actionTaken` |
| `routes` | Buttons shown | comma-separated (e.g. `Approve,Reject,Request More Info`) |
| `inputDataFile`/`inputAttachmentsPath` | Pre-populate | path relative to payload |
| `outputDataFile`/`outputAttachmentsPath`/`outputDoRPath` | Save | path relative to payload **or** variable |
| `allowDelegation`/`allowSharing` | Inbox delegation/sharing | `true`/`false` |
| `htmlEmailTemplate` | Custom email template | absolute CRX path (use `/apps/{project}/…`) |

### Automated Process Steps

```xml
<node2 jcr:primaryType="cq:WorkflowNode" title="[TITLE]" type="PROCESS" x="300" y="280">
  <metaData jcr:primaryType="nt:unstructured"
    PROCESS="[PROCESS_CLASS]" PROCESS_AUTO_ADVANCE="true" PROCESS_ARGS="[ARGS]"/>
</node2>
```

| Step | PROCESS class | Auto-advance |
|---|---|---|
| Set Variable | `com.adobe.granite.workflow.core.process.SetVariableProcess` | true |
| Invoke FDM Service | `com.adobe.fd.workflow.aem.process.InvokeFormDataModelServiceStep` | true |
| Generate Document of Record | `com.adobe.fd.workflow.aem.process.GenerateDocumentOfRecordStep` | true |
| Send Email | `com.day.cq.workflow.process.SendEmail` | true |
| Convert to PDF/A | `com.adobe.fd.workflow.aem.process.ConvertPDFStep` | true |
| Adobe Sign — Send for Signature | `com.adobe.fd.workflow.aem.process.AdobeSignStep` | **false** (waits) |

### OR Split / AND Split / AND Join / Goto
```xml
<nodeA jcr:primaryType="cq:WorkflowNode" title="Route Decision"  type="OR_SPLIT"  x="440" y="280"><metaData jcr:primaryType="nt:unstructured"/></nodeA>
<nodeB jcr:primaryType="cq:WorkflowNode" title="Parallel Review" type="AND_SPLIT" x="440" y="280"><metaData jcr:primaryType="nt:unstructured"/></nodeB>
<nodeC jcr:primaryType="cq:WorkflowNode" title="AND Join"        type="AND_JOIN"  x="600" y="280"><metaData jcr:primaryType="nt:unstructured"/></nodeC>
<nodeD jcr:primaryType="cq:WorkflowNode" title="Return"          type="GOTO"      x="600" y="400"><metaData jcr:primaryType="nt:unstructured" GOTO="node1"/></nodeD>
```

## Transition Node

```xml
<transition0 jcr:primaryType="cq:WorkflowTransition" from="node0" to="node1" rule="" x="90" y="280">
  <metaData jcr:primaryType="nt:unstructured"/>
</transition0>
```

**OR-split transition with `actionTaken` (official pattern — copy verbatim):**
```xml
<transition1 jcr:primaryType="cq:WorkflowTransition" from="node3"
  rule="function check(){var meta=workItem.getWorkflowData().getMetaDataMap();return meta.get('actionTaken',String)=='Approve';}"
  to="node4" x="510" y="230"><metaData jcr:primaryType="nt:unstructured"/></transition1>
```

> `actionTaken` is the **Route Variable** on the Assign Task step. It holds the exact button
> label clicked (`Approve`, `Reject`, …). Use the same variable name in every transition and
> declare it in `metaData/variables`. Use capital-S `String`, not `string`.

## Workflow Variables

Declared in `metaData/variables`. Required when the model is marked for external data storage
(then variables are the only option for data/attachments/DoR).

```xml
<variables jcr:primaryType="nt:unstructured">
  <actionTaken      jcr:primaryType="nt:unstructured" type="String"  description="Route variable — Approve/Reject"/>
  <approverComments jcr:primaryType="nt:unstructured" type="String"/>
  <applicantEmail   jcr:primaryType="nt:unstructured" type="String"/>
  <submittedData    jcr:primaryType="nt:unstructured" type="JSON"    description="Form payload"/>
  <formAttachments  jcr:primaryType="nt:unstructured" type="ArrayList" description="ArrayList of Document"/>
  <generatedDoR     jcr:primaryType="nt:unstructured" type="Document" description="Generated DoR PDF"/>
</variables>
```

**Supported types:** `String`, `Long`, `Double`, `Boolean`, `Date`, `JSON`, `XML`, `Document`, `ArrayList`.

## Generate Document of Record Step

```xml
<metaData jcr:primaryType="nt:unstructured"
  PROCESS="com.adobe.fd.workflow.aem.process.GenerateDocumentOfRecordStep"
  PROCESS_AUTO_ADVANCE="true"
  PROCESS_ARGS="formPath=/content/forms/af/{project}/[FORM_NAME],locale=en,dorOutputPath=[Payload_Directory]/DocumentofRecord/DoR.pdf"/>
```

Prerequisites: "Generate Document of Record" enabled on the form (Form Model tab), or the form
uses an XDP/PDF model.

## Set Variable Step PROCESS_ARGS

Single: `variableName=actionTaken, variableType=String, variableValue=pending`

Multiple (semicolon-separated), reading submitted data:
```
variableName=applicantEmail, variableType=String, variableValue=${payload.jcr:content/data/applicantEmail}; variableName=requestAmount, variableType=String, variableValue=${payload.jcr:content/data/amount}
```

## x/y positioning convention

Start `x=20,y=280`; each step `x += 140`; split branches `y ± 100`; End at the final x.
