## Run output convention (mandatory)

All activities are executed by agents. Every agent/skill invoked for a use case **MUST persist its
output as a file** under the **`.claude/agents/runs/`** folder, inside a per-use-case **run directory
whose name starts with the execution date and the exact form name**:

```
.claude/agents/runs/{YYYY-MM-DD}-{formName}/
```

- `{YYYY-MM-DD}` — the date the work is **executed** (today's date at run time).
- `{formName}` — the **exact** kebab-case form node name the work is for (the primary form for a
  multi-form program; use the brief/program name only when no single form applies).

### Organize each run by SDLC cycle (mandatory)

Inside the run directory, files are **grouped into SDLC-cycle subfolders** — do **not** dump every
file flat at the run-directory root. Each phase writes its deliverable into the folder for its cycle:

| Subfolder           | SDLC cycle · lead         | What goes here (the phase's **end-deliverable** only)                              |
|---------------------|---------------------------|------------------------------------------------------------------------------------|
| `plan/`             | PLAN · planwright         | `planwright.md`, `user-stories.yaml`, `solution-architecture.yaml` |
| `design/`           | DESI · draftsmith       | `draftsmith.md`, `component-design-spec.yaml`, `test-cases.yaml` |

## Forms type: Core Components

This project uses **AEM Forms Core Components** (recommended for AEMaaCS).
- The project's adaptive form components proxy `core/fd/components/form/...`
  via `sling:resourceSuperType` (e.g. the form container extends
  `core/fd/components/form/container/v2/container`).
- Prefer Core Components resource types for new components.
- Form container: `core/fd/components/form/container/v2/container`
- Legacy Foundation guide resource types (`fd/af/components/...`) appear only
  in template/policy definitions for backward compatibility — do not author
  new components against them.

## Build and deploy

```bash
# Build and deploy all modules to local AEM SDK
mvn clean install -PautoInstallSinglePackage

# Deploy only ui.apps (faster for component changes)
mvn clean install -PautoInstallPackage -pl ui.apps

# Run unit tests only
mvn test -pl core
```

Build requires Java 11+ and Maven 3.3.9+ (enforced by maven-enforcer-plugin).

### Deployment is centralized in Forgemaster (mandatory)

In a delivery run through the agent pipeline
(`formwright → groundsmith → assembler → forgemaster → sentinel`),
**deployment is owned by the `forgemaster` lead** — it runs the single authoritative
`mvn clean install -PautoInstallSinglePackage` after all artifacts are authored (including the
**page embed** produced by `assembler`), confirms the deploy, and writes the code-quality report
(with the deployment artifact names) to `deployment/`.

- When a build/integration/assembly skill (`create-adaptive-form`, `create-AdaptiveFormFragment`,
  `create-fdm`, `create-form-clientlib`, `create-form-rules`, `create-workflow`, `migrate-form`,
  `composer`, …) runs **as part of a pipeline delivery**, it **AUTHORS artifacts only and SKIPS its
  own `mvn` build/deploy step** — even steps marked "MANDATORY". Forgemaster does the one build+deploy of
  record. This overrides any deploy instruction inside the individual skill.
- A skill invoked **standalone / directly** (not via formwright/groundsmith/assembler) still runs its
  own deploy step as written, so direct use keeps working.
- The build/integration/assembly leads (formwright, groundsmith, assembler) must pass "author only —
  do not deploy; defer to Forgemaster" to every skill they delegate to. Because `assembler` runs **before**
  forgemaster, the updated "Test Adaptive Form" page is included in that one deploy.

## Common mistakes to avoid

- **NEVER** author new components against Foundation guide resource types
  (`fd/af/components/...`) — this is a Core Components project
- **NEVER** hardcode `/content/forms/af/` paths — use variables from `.aem-forms-config.yaml`
- **NEVER** leave ResourceResolver open — always use try-with-resources
- **NEVER** hardcode secrets in `.cfg.json` — use `$[secret:keyName]`
- **ALWAYS** set `aria-label` on every form field
- **ALWAYS** include both OSGi service AND JCR node for custom submit actions
- **NEVER** run `mvn` build/deploy from a build/integration/assembly skill when it's part of a
  pipeline delivery — deployment is centralized in the `forgemaster` lead (see "Deployment is centralized
  in Forgemaster" above); author artifacts and defer
- **NEVER** embed a form into a Sites page by hand — invoke the `composer` skill; it runs before
  forgemaster so the updated page deploys, and it **replaces** (never stacks) the previously embedded form
- **NEVER** hand-author a Forms artifact (form, template, theme, component,
  submit action, prefill service, rules, schema, tests, page embed) by copying an existing
  one — **ALWAYS** invoke the matching skill first (see "Skill usage is
  mandatory" above), no matter how the request is phrased
